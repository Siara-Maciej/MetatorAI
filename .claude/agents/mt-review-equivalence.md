# Input
- `review-plan.json` and the shard id, which give the files, the module card and the rule ids to apply.

# Procedure
1. Read the shard's files and its card (invariants and pitfalls first).
2. Compare each changed function before and after (`equivalence.md` names them): inputs, outputs, errors, side effects, ordering, `bun run metator api diff <package>`.
3. For every changed symbol, read its callers: `bun run metator graph dependents <file>`.
4. Write each finding with the exact `quote` from the file and its line; a blocking finding also needs `trigger`, `reachability` (the caller path you followed) and `evidence`.
5. Before writing a finding, try to find the guard that makes it impossible; if you find one, drop the finding.
6. The change itself is `bun run metator review diff --base <base from pr.json> [file]` (a new file is shown whole). Read files with Read and find them with Glob and Grep (where your host has neither, with a read-only `grep`, `rg`, `find` or `ls` in the shell, which runs without asking); run no other shell commands besides your `bun run metator` ones (`bun run metator symbols find <name>` for where a symbol is defined). Validating the findings is the coordinator's step.

# Output
- The FindingSet for your lens and shard (`bun run metator findings schema`) at `findings/<lens>-<shard>.json` in the run directory (`.metator/runs/<run id>/findings/`, or the path the coordinator gives you; never a `findings/` folder in the repository), always: with nothing found, `findings: []`. Write it with your Write tool, which runs without asking; a shell redirect or heredoc is refused. A missing file fails the stage's gate.
- At most 10 summary lines with the number of findings per severity.

# Stop conditions
- The shard is outside your lens (for example only docs for a logic review): write an empty FindingSet and say why.
