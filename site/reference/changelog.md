# Changelog

What changed on the default branch, newest first, in terms a user sees. MetatorAI is pre-alpha and installed from a checkout, so there are no numbered releases yet.

Every file MetatorAI writes carries a `schemaVersion`. When a document gets a new version, it is named here. Older files keep loading.

## November 2026

- Chats are threads, one per topic ([Chats and threads](../use/threads.md)). A thread (`.metator/threads/<id>.json`, Thread v1) keeps the chat's title, the summary its agent writes (`metator thread summary`), the runs started from it and facts the daemon adds (a run started, done, aborted or stopped for you; the chat closed or reopened). The chat agent reads it first in every session (`metator thread show`), the same on Claude Code and Copilot CLI, and asks before it opens a new thread for a new topic (`metator thread new --carry`). `metator thread list|show|new|summary|close|reopen` and the daemon's `/threads` routes; the state carries `threads: { open, closed, updatedAt }`. A chat's pane names its thread in the layout (`threadId`, Layout v5). Closing a thread ends its terminal and never stops a run; reopening continues its host session, or starts a new one that is told which thread it continues. A run no chat started is "without a chat".
- Leftovers from a second real Claude Code run of the chat:
  - A card made from an agent's own words now shows the agent's own question: the one its choices stand under, else the one its turn ends with, else the sentence that tells you to answer ("Tell me how to proceed."). Nothing is glued to it any more (no "Which option?"); a message with no such sentence shows its first sentence alone, never the tail of a sentence cut off at the top of the screen. A greeting that lists what you can do and ends with "What would you like to work on?" is no question. Bullets are choices only under a question or a cue to choose; the lines under an item are that item's, never a choice or a prompt of their own.
  - A host's approval of a command that runs over several lines no longer carries Claude Code's `│` gutter in `command`, and a quoted argument Claude Code wrapped at words is one line again. When the guard is why the host asks, the question carries the guard's reason in `reason` (Question v5; the `pre-tool` hook keeps it per pane, GuardAsked v1).
  - A worker writes a Markdown artifact (`quick-review.md`, `build-log.md`) with exactly one command, which runs without asking: `metator run write <artifact> --run <run> <<'EOF'` … `EOF`. Its first message says so, and so does the agent file of a worker without a Write tool (`mt-quick-review`, `mt-diagnostician`, `mt-review-responder`). Before, `mt-quick-review` was told to use a Write tool it does not have.
  - `metator session tell` and `interrupt` to a session that ended refuse with `TRANSITION_DENIED`, send and queue nothing, and name the live sessions of the task (also in `details.live`).
- The app, first stage of the conversation agent: **+ New run** opens the repository's conversation agent (`mt-chat`) as the **chat**. A commit or push the agent asks for is a card headed by the command that says it needs your consent. A quick change ends with the card **Quick change ready: look at the diff** (**Open diff** opens the run's Changes and leaves the card, **Fine** closes it); **This grew past quick** offers **Continue as full** and **Keep as quick**. **Debug changes (N)** on Home and in a task's terminals lists the recorded debug edits and removes one or all. One that can no longer be taken out as recorded stays, marked with the reason, until you take it out by hand or **Forget** it; one you took out by hand is said to be gone.
- Fewer approval prompts (`guard.prompts`, MetatorConfig v14, default `metator`): on both hosts the `pre-tool` hook now answers `allow`, with the reason, for MetatorAI's own commands, commands that only read, edits inside the repository and the repository's own checks (the gates' steps and the package's `test`, `typecheck`, `lint` and `build` scripts). A chain passes only when every part qualifies. Everything else keeps your host's prompt; `never` and `ask` win as before. MetatorAI's commands that are your decision (`run approve`, `run answer`, `config set`, `setup`, `quick start --override`, …) are asked about by name. `guard.prompts: host` keeps your host's own prompts for everything. Copilot CLI sessions are started with a matching `--allow-tool` list.
- A commit can no longer take debug changes by adding and committing in one call: the commit guard reads the whole command line (`git add src/a.ts && git commit`, `git add -A`, `git stage`, `commit -a`, paths named on the commit, a `cd` before them).
- A line the daemon types into a session (a relay, a nudge, a notice, a card's answer typed for you) is no longer taken for your own typing by the host's user-prompt hook: the daemon keeps a hash of each (`.metator/typed/`, PaneTyped v1). Its own lines give no consent and no "told directly" note; your card answers are your word.
- A card is made from an agent's own words more carefully: numbered items that are themselves questions or explanations are no longer offered as choices (the card asks the first question and takes your words), a status report with `Label: value` bullets is no question, and "let me know if …" is no wait. A panel your host draws at the right of the message is no part of it.
- `metator setup` installs the hooks unless you say `--no-hooks` (and says what is missing without them), and `metator init` proposes a quick gate with your typecheck and test scripts beside the lint, so a quick run can pass its gate. `metator quick start` refuses up front when `gates.quick` has no steps.
- Dangerous commands have three levels, the same on Claude Code and Copilot CLI, from one list in the configuration (`guard.commands`, MetatorConfig v13): `never` (force push, `git reset --hard`, `git clean -f`, rewriting history, deleting the repository) is denied for every agent; `ask` (`git commit`, `git push`, `git merge`, `git rebase`) runs only with your consent, given by a click on your host's approval prompt or by your word in the chat ("commit", "push it"); the rest is free. A consent in words holds for `guard.consentMinutes` (10) and for one command; it comes only from your own message, through the new hook `UserPromptSubmit` → `metator guard user-prompt` (run `metator generate --hooks` to install it). Copilot CLI is also started with `--deny-tool` for every `never` command. Before, a fixed list was denied and a commit was not guarded at all.
- The conversation agent `mt-chat` (installed by `metator setup` and `metator agents update`, for both hosts). It takes the lightest way that fits what you ask and suggests it; you decide: it answers or edits directly, starts a quick run, or names a workflow and starts a full run whose conductor works in its own terminal (`metator run new`, then `metator run start`; the chat stays the task's main terminal). It never commits or pushes by itself. `GET /supervisor` has `chatAgent` when the repository holds the agent's host file. The chat's pane may now open a run's conductor session, and it is bound by no run: a run that works in the same checkout no longer blocks the chat's edits.
- Quick changes: the workflow `mt-quick` (build by a worker in its own terminal, the quick gate on the changed files, one short review by the new agent `mt-quick-review`, whose `quick-review.md` may send it back once through the gate `metator quick reviewed`; no plan, no approval gates, no publish) ends with an uncommitted diff and the card **Quick change ready: look at the diff**; **Fine** ends the run, and no drive starts for it. `metator quick check [--files a,b] [--diff] [--task "<text>"]` says without a model whether a change is small enough (`{ quick, escalators: [{ id, why, source }], thresholds, files }`; the limits are `quick.maxFiles`, `quick.maxLines`, `quick.maxDependents`). `metator quick start --task … [--files] [--override "<your sentence>"] [--here|--worktree]` refuses while an escalator trips unless you keep it quick in a sentence (recorded with the run, QuickRun v1); a change that reaches another repository is never quick. When the real diff grows past the limits the run asks **This grew past quick**: **Keep as quick**, or **Continue as full**, which starts a full run on the same working tree and closes the quick one.
- Debug changes: `metator scratch begin` and `metator scratch end [--note]` record a direct edit that is not meant for a commit as a patch (`.metator/scratch/`, ScratchRecord v1); `metator scratch list` shows what is still in the working tree and `metator scratch drop --id … | --all` takes it out again, leaving your other work in the same files. A record whose lines changed since can no longer be taken out as recorded: it is reported (`failed`), stays listed with `state: "changed"` and why, still counts and still stops a commit of its file, until you take the lines out by hand and dismiss it (`metator scratch forget --id …`, `POST /scratch/forget { ids, by }`). A record leaves by itself only when no file holds its lines any more, and the response that removes it says so (`gone`). Nothing is forced. A `git commit` an agent runs that would hold a recorded change is stopped with the files until you say "commit anyway". The daemon has `GET /scratch`, `POST /scratch/drop { ids?, by }`, and `scratch` (the count) on `/state`, for each repository of a folder too.
- Steering a task's sessions: `metator session list [--task <run>]` shows a task's sessions (pane, repository, role, agent, state); `metator session tell <pane> --text "<your words>"` types your words into a session when its agent is idle (queued until then, never over a prompt or a question it asked); `metator session interrupt <pane> --text …` sends Esc first. Only the task's main chat or a person may; what the chat relays is typed behind `[metator] From the person, through the main chat: ` and recorded in the run's activity. When you type into a run's session yourself, the task's main chat is told in one line (`[metator] The person told <repo>/<agent> directly: "…"`). Routes: `GET /sessions`, `POST /panes/:pane/tell`, `POST /panes/:pane/interrupt`.
- A run's conductor in a pane sees each stage's gate script in its first message and runs it before it advances. A pane's agent is no longer refused `metator run …` commands as if `metator run drive` drove it: a conductor delegates and a chat starts runs.
- An agent that asks you in its own words now reaches you. Before, when an agent (a run's conductor or worker, or the chat) ended its turn with a question or options in prose and waited, no card came, and the supervisor kept nudging it every 90 s. Now its last message becomes a card with the whole message and the choices, and the run needs you. Your choice is typed into the pane, and the supervisor never nudges it while the question is open. In `GET /inbox` `panes`, such items carry `runId` and `question.text`. The agents' prompts now say to ask with `metator run ask`.
- A conductor whose session is started again in its pane (the supervisor's resume, `metator run start`) keeps the screen the last session left above the new one, as a restored pane does. The resume line is never typed into a pane whose agent waits for the person (a host's prompt on its screen, or an open question).
- A resumed session goes on by itself. After a restart or a Continue, a resumed conductor or worker idle at its prompt is told once to go on (`[metator] Your session was resumed after the daemon stopped …`), never while a person holds the keyboard. The supervisor does not nudge it as well. Before, Claude Code came back at "Interrupted" and waited.
- The scenario host (tests, demos) counts an agent's starts per run: the conductors of two runs in one daemon each begin at the agent's first entry. Before, the second run's conductor began at the entry meant for a resumed session, so after a Continue that entry showed twice.
- Agents' sessions survive the daemon. A pane whose process went with the daemon (SIGTERM, SIGKILL, a crash), or that a signal ended, is **paused**, not ended: `paused: { at, why: "daemon-stopped" | "process-lost" }` in the layout (Layout v4), with its session id and last screen (saved every 5 s, `--screens-ms`). The next `metator serve` resumes each one in the same pane, under the screen it left; `--no-restore` leaves them paused. `metator run continue` (with a daemon) and `POST /runs/:run/continue` continue a whole task across repositories, returning `{ resumed, drives, skipped }`: paused panes, the chat the task was given in, and every active run nothing carries (its conductor, else its drive). `POST /panes/:pane/continue` continues one paused pane. A process a signal ended now exits with 128 + the signal (SIGHUP: 129). (ADR-0092, Proposed.)
- The chat a task was given in is told, in one line typed to its agent, when the task is done, closed, stops for you or waits for your approval, once per event and only while the agent is idle.
- A host's permission question carries `command`, the whole command it asks to run (a long or multi-line one too; Question v4). Its `prompt` starts with the command's first line: `metator workflow list — This command requires approval`.
- Panes' screens are read by `@xterm/headless` (approved 2026-11-20), so wide characters (emoji, East Asian letters) and scroll regions read as on screen.
- The app after the daemon stops: a terminal whose host stopped with the daemon reads **Paused — the daemon stopped**, keeps its last screen, and has **Continue**; a session's badge counts paused sub-terminals. **Continue task** on a task's terminals (and its main terminal's tile) continues every paused terminal and every run nothing drives, and says what it resumed and skipped. A host's question shows the start of its command, cut to two lines; a click shows the whole command. Reloading the app, or opening it in a new window, shows the same task, terminals and cards.
- A pane without a run that asks now reaches you. Before, when the chat where you describe a task (no run yet) waited on its host's prompt, such as Claude Code asking leave to run `metator workflow list`, nothing reached the inbox. Now Home shows the question as the chat's own card, with the pane, its repository and its choices, and the chat's frame in **Terminals** says **needs you**. A host's numbered menu is offered choice by choice, also for a run's panes. The one you pick is typed into the pane as its number, then Enter. For scripts: `GET /inbox` has `panes` (`{ kind: "pane", repo?, paneId, label, role?, host, question }`), answered with `POST /panes/:pane/answer` (ADR-0091, Proposed).
- A pane's state gives its prompt in one readable line (`Bash command: metator workflow list — This command requires approval`), at most 200 characters, read from the screen as it is drawn instead of from the raw output with its escapes and spinner frames. `metator pane read` and `GET /panes/:pane` return the screen as shown.
- The child runs of a system plan start as sessions you see: `metator system plan run` (and the system run's status gate) opens each child as its own conductor session, a pane in its repository's worktree on the default interactive host (the system run's own when it is installed, else the first installed of `supervisor.hostOrder`), and its conductor delegates its workers as panes, several at once for a stage with `parallel` agents. With no daemon serving the repository, or no interactive host installed, the child is driven in the background as before. Each started step says which (`session: { paneId, host }`, or `noSession` with why and `drive`), at a terminal (`session in pane w1:p1 on claude`), in the gate's message and in the run's activity (ADR-0090, Proposed).
- Terminals by task: **Terminals** opens on a task with its main terminal (the chat where you gave it, else its conductor) and one tile per repository session working on it, side by side; a session's badge (`2 sub-terminals · 1 finished`) opens its own view with its workers and **Tasks › task › repository** back. A terminal whose work is over stays, read-only, with **Finished — …** (or **Ended with code N** in red) and **Close**; **Close finished (N)** closes them all (on a task's view, its sub-terminals too). Two repositories' panes with the same id (each repository numbers its own) are two tiles. The go-to picker lists a task's terminals as `task › repository › worker`; **Workspaces** keeps the tabs as before.
- `metator run wait` and `metator pane wait` no longer fail with `ECONNRESET` after 10 seconds: the daemon keeps a waiting request open for as long as its `--timeout` asks, so a conductor can wait for a worker that works for minutes.
- Panes are no longer removed by the daemon. A finished run's panes, a collected worker's pane and a pane whose process exited stay, ended, with why (`ended`: `run-finished`, `collected` with the worker's one line, `exited` with the code) and their last screen, read-only, until a person closes them; `POST /panes/close-ended` closes them all (or one run's). `metator run collect` returns `paneEnded` (`paneClosed` is always false now). A chat pane whose agent ran `metator run new` remembers that run as `startedRun`. The layout file is Layout v3.
- A scripted (scenario) agent can run a command: the step `run: <command>` (AgentScenario v2) runs in its directory with its session's environment, so a scripted conductor delegates and collects workers with `metator run delegate|wait|collect` like a model does. A failing command ends the session with its code.
- **Retry this step**: a step of a system plan whose child run was aborted can be re-opened by a person, from the system run's bar, the step in its plan, `metator system plan retry <plan> <step> --by <name>` or `POST /system/plans/:plan/steps/:step/retry`. The step is pending again with its old run in its history (`previousRuns`, SystemPlan v2), and the system run starts a new child for it. The old worktree stays for a look.
- An answer no longer ends a run. When an agent finds nothing to do, the decision is **Finish the stage** (the stage passes; its gates and tests judge what is there) or **Do it anyway**. "Close the run" is gone from it, and a headless run finishes the stage instead of aborting. Only a person closes a run, with `metator run close --aborted --reason` or **Close run…**.

- Every child run of a system plan works on its own branch, in its own worktree, made from the repository's HEAD (or `--base`), even when the checkout has changes. Before, a step alone in its repository ran in the checkout, on the default branch, and its publish stage stopped to ask which branch to create. A run that worked in the checkout (the form's worktree box unticked) now gets its own `metator/<run>` branch at publish, made by `mt-pr-author` without asking.

- The app is simpler at first sight, with details one click away, in three levels. **Home** shows one decision at a time, with **3 waiting** and **‹ Previous** / **Next ›** (`k` / `j`); the ids, evidence, "since you left", what each answer does and the command it writes are under the card's **Details**. With nothing to decide Home lists the tasks in short and offers **Describe a task**. A task's page (a system run, a run with child runs) has Overview · Changes · Activity: the one thing to decide, the flow and the steps by repository. A step's page has Overview · Terminal · Changes · Activity and **Task › step** back to its task; the Plan tab is gone, the step's plan is on its Overview. The sidebar, Home, the Board and page heads say one of four words (`needs you`, `working`, `blocked`, `done`), with no run ids, hosts, ages or full stage lines; those are under **Details** on the step's page. Finished tasks are hidden behind **Show finished (N)**, also in the Board's Done column. Each decision has its own address (`#/inbox/<repository>/<run>/<question>`): opening one from the sidebar or a page shows exactly that card. A plan's card has its actions above the plan, with the system plan's step tables folded under its flow; a decision has one set of controls everywhere (choose an option, one button sends it). A run that asks with no session open still offers **Open a session**. The sidebar's places are Board, Terminals, Backlog and Settings; Reviews and the Overview (now **System**) are parts of Settings, and their old addresses lead there.
- Nobody edits a plan by hand any more. At a plan's approval you approve it or ask for changes in words: the run goes back to its planner, whose prompt quotes you and asks it to revise its plan, not to start over. A system run's plan approval now sends its plan back the same way (it used to escalate). Asking for changes while the plan's lint has errors passes those errors to the planner too. The plan's view (`GET /runs/:run/plan`, `GET /system/plans/:plan`) shows the version the planner replaced (`previous`) and what changed, step by step (`changes`). The routes that saved a plan (`PUT /runs/:run/plan`, `PUT /system/plans/:plan`) are gone; the map editor stays.

- The app: plans are no longer edited by hand. A plan's approval card shows the plan in full, with **Ask for changes** (your words go to the planner as the gate's Reject reason) and what changed since the planner's previous version. The sidebar lists parent tasks (a system task, a run with child runs, a run) with their progress and needs-you counts, each unfolding into its steps by repository; the Inbox lists the decisions. The Board's top level shows one card per task and opens each task's own board. A system task's flow is shown once, on its page (the system run's Plan tab).
- At a terminal, a command with a text for people prints only that text, with no JSON line after it: `status`, `inbox`, `run status`, `doctor`, `run ask`, `system plan status`, `system plan show`, `issue list` and the help. A pipe, a script and `--json` get the JSON line as before.
- A system run's status gate starts the next wave itself and goes on waiting. The waits between waves are no longer failures in its history, and they spend no loop. A decision card shows them as `status waits: started the next wave: …`. A gate's command reads with its paths filled in (no `{runDir}`).
- `system plan status`, `system plan show` and `issue list` print text at a terminal. A run started from a Backlog task takes the task's title as its task; the body is the run's `task.md`, which its agents read.

- The app: Overview → Dependencies and a system run's Plan tab draw a system plan as a flow (waves, repositories, an arrow per dependsOn, pending steps dashed, the critical path). A new **Board** puts every piece of work in To do · Planning · In progress · Review · Done, with filters and swimlanes. Each run of `/state` carries its `phase`. Two steps of one repository in one wave each get a worktree. An answer's confirmation says what the run did with it.
- Every question an agent asks in its terminal gets its own card, not only the first. A card's answer is typed into the pane at once (it used to wait up to the daemon's next check). An answer typed in the pane is recorded with the person at its keyboard and the words typed, and its card goes. A card that comes after the pane answered is refused and types nothing; while a person holds the pane's keyboard, a card answer is refused with their name.
- `metator run ask "<question>" --option <a> … [--wait] [--timeout <ms>]`: an agent in a terminal asks the person through the inbox and, with `--wait`, gets the answer printed; `--question <id> --wait` waits again.

- A system run no longer escalates when a child escalates: it waits, `blocked by <child>: needs you`, and goes on by itself once the child is resumed. It escalates when a child is closed as aborted, or after six hours.
- An escalated run says why in one sentence (`stop`): a person's Reject reads `stopped: ana rejected plan-approval: <reason>`; the tries wording (`tried build 3 of 3 times`) only when the tries are really spent.
- The gate that approves a run's plan refuses Approve on its card and in an answer while the plan (`plan.json`) has lint errors; the card's Approve is `disabled` with the problems. `metator run approve` at a terminal still approves.
- `system.roots` is an option (repository scope): the directories that hold the applications' checkouts. **Save roots** in the app writes it.
- Discover in a place with no map lists everything as what the map lacks (`mapExists: false`), and Write creates it.
- A question an agent asks in its terminal with options (`Which currency? [PLN / EUR]`) reaches the inbox as that agent's question, in its own words, with its options; the option you pick is typed into the pane. A host's own permission prompt stays a permission.
- `run status` names the host that drives the run (`host`), also for a host that keeps no session.
- A drive whose repository disappears stops its agent and itself.

- The app: an aborted run reads `aborted` (with its reason on hover) and a finished run's line says how it ended; a system plan's step is numbered by its place in the deploy order (`step 2/2`) in the sidebar and on its cards; a task's run is a link with its state.
- The app: an agent's question on its terminal is a `TERMINAL` card in its own words, with its answers; **Attach and answer in the pane** lands on that pane, focused, with the keyboard taken. A plan with lint errors closes **Approve** on its card, with **Fix the plan**. A system run's page says its steps done and which child it is blocked by. `system.roots` is edited as a list, and Discover with no map shows the map it proposes.
- A system run (`mt-system-change`) waits for its child runs instead of spending its waves in seconds: while they work it reads as working and says what it waits on; it starts the next wave when one is done, and escalates at once when a child escalates (or after six hours). Its gate is `metator system plan status --gate`; `run drive --gate-wait <ms>` says how often it looks.
- A system run's child runs are driven as they start, on the system run's host; a run nobody chose a host for takes the first host of `supervisor.hostOrder` that can start here.
- One Approve on a system run's plan-approval approves the system plan too; a plan with lint errors refuses it, and the daemon marks the card's Approve `disabled` with the reason.
- A human gate always has its approval card, whoever moved the run there (a drive, a conductor, a person); answering it passes or rejects the gate.
- In a folder, `run start`, `run delegate`, `run workers` and the other conductor commands reach the repository they run in, and a pane's own calls reach its repository.
- `POST /runs/:run/pty-open` starts the run's conductor (as `run start`), not a plain session; `POST /runs/:run/drive` starts a background drive.
- A proposal decided in the Backlog (or with `issue decide`, `issue rm`) leaves Needs you. A finished run's panes close.
- In a folder, each repository scans its intake on its own `intake.everyMs`.
- A worker's terminal question is the worker's, at its stage; it no longer makes the conductor read as waiting.
- A step of a system plan without a worktree no longer shows the system run's plan files as its change.
- An escalation says the failed command's message and hint (not its JSON) and how often the stage was tried (`attempts`).
- `metator system discover --write` in a folder writes the folder's map into one of its repositories (`--repo`).
- The desktop app: the Plan tab shows the run's plan with its lint at each step and field, and changes it (**Edit plan** as fields, **Edit as text** as JSON, **Check**, **Save…** with what changes, a conflict offers **Reload** or **Keep my edits**). A system run's Plan tab shows the system plan with its steps per repository, waves, child runs, approval and **Approve**; **Overview → System** lists the system plans and edits the system map, its roots and **Discover**. Every artifact of a run opens read-only.
- A run nothing works on offers **Open a session** (its conductor, with the host to use) and **Drive in background**, on its page and in the Inbox, which now says what is true about the open runs. **Attach and answer in the pane** takes you to the pane. A finished run reads `done`; a worker that ended with code 0 reads `finished`. A system run's steps sit under it in the sidebar across repositories with the right count. The dependencies graph keeps finished runs of the last day, dimmed.
- The daemon's API answers with MetatorAI's envelope and these statuses: 404 when something is not there (`NOT_FOUND`), 403 when a pane may not do it, 400 for everything else. A request body that does not fit its route is refused with `USAGE` before anything runs. Paths and answers are unchanged.
- Through the daemon, as in the terminal: a run started in a worktree gets its dependencies; an answer can carry `always` and becomes a policy; closing a run takes `removeWorktree` (and `force`); a `since` that is not a time is a usage error.
- A WebSocket on `/ws/pty/<run>` no longer starts a session: it connects to the one the run has. Start one with `POST /runs/<run>/pty-open` or `metator run start`.
- At a terminal a failed command also prints what is wrong and what to do about it on stderr.
- The desktop app has one sidebar instead of three columns: **Needs you** on top (each row opens its decision), the runs with their panes under them, then Terminals, Backlog, Reviews, Overview and Settings, and **+ New run** with **Form…**. The counters left the top bar; the counts are in the headings.
- A run has one page with the tabs Overview, Terminal, Plan, Changes and Activity (keys `o` `t` `p` `d` `l`). The old addresses (`#/session/…`, `#/plan/…`, `#/review/…`, `#/briefing/…`) open the right tab. The Overview counts the files of the run's change from the same source as Changes.
- A run reads `needs you`, `working`, `escalated`, `done` or `idle`; `done` stays marked until you open the run. The Daemon and Graph screens are now **Overview** (Daemon, Dependencies).
- With no run the app offers **Describe a task**. An answer is confirmed in words. `?` filters as you type; `j`/`k` and the arrows move in every list.
- Words: a unit of work is a run (**+ New run**), a session is the live agent process, a task is a backlog item, the multi-pane screen is **Terminals**.
- The desktop app, tidied: every screen about one run (Session, Plan, Changes, Briefing) has the same head with links to the other three. A pane reads the same on every screen, in four words: `working`, `asks`, `idle`, `exited`; a shell at its prompt is `idle`. **need you** in the top bar, **Needs you** in the Inbox, the Graph and the Daemon screen count the same runs, escalated ones included.
- Opening a run's **Session** screen no longer starts a terminal session: **Open a session** does. An escalated run's Session screen offers **Resume** and **Close run…**; a finished one says how it ended.
- `?` opens the list of keys on every screen. Menus and the prefix chip show the real prefix key (`ctrl+b z`) instead of the word "prefix".
- The runs panel names runs whose record cannot be read, with the file to restore. Dialogs keep the focus inside them and give it back when they close; the lines of a diff are one Tab stop, moved through with the arrow keys.
- `metator ui`, the full-screen view in the terminal, is removed: the desktop app is the graphical front. At a terminal `metator status`, `inbox`, `run status`, `doctor`, `help` and every `--help` now print text you can read on stderr; stdout keeps the one JSON line, and `--json` prints only that line.
- New names, with the old ones still working: `metator run new` (was `run init`), `run take` (was `run attach`), `issue rm` (was `issue drop`), `system plan status` (was `system status`), `docs schema` (was `docs claims-schema`), `meta schema agents|skills` (was `meta agents-schema`, `meta skills-schema`).
- `metator help --for person|agent|hook|ci` lists the commands of one audience.
- The run can be named as a word: `metator run status <run>`, also for `board`, `brief`, `activity`, `stop` and `close`. `--run <id>` still works.
- Who acts when `--by` is left out is one rule everywhere: `$METATOR_USER`, else git's `user.name`, else your login name. `--by` is no longer required for `run take`, `run message`, `findings react`, `review notes add` and `review notes send`; `run approve`, `mrs send` and `mrs resolve` still require it.
- `metator run continue` on an escalated run, at a terminal, asks whether its cause is fixed and resumes it on a yes. Without a terminal it still refuses and names `run resume`.
- A `Deny` answer no longer asks for a reason in the terminal: only `Reject` and `Other` ask for your own words.
- `meta check-all` runs the same checks in the order of the command list.
- Documentation rebuilt in four sections: Guide, Use, Repository, Reference. Old addresses changed.
- Automatic intake: rules under `intake` turn issues from GitHub, GitLab or Jira into tasks and runs (`metator intake rules`, `scan`, `status`).
- Reviews of your own pull requests: `metator mrs list`, `show`, `scan`, `triage`, `send`, `resolve`, and the `mt-review-response` workflow. New document: `PullRequestReview`.
- MCP servers in the configuration (`mcp`), written to `.mcp.json` by `metator generate`. `metator mcp` serves MetatorAI's reading commands as MCP tools.
- Options with three scopes (user, repository, run): `metator config list`, `get`, `set`, `unset`. New document: `UserOptions`.
- A backlog of tasks: `metator issue list`, `add`, `propose`, `decide`, `start`. New document: `Issue`.
- Notes on a change: `metator review changes` and `metator review notes`. New document: `ReviewNotes`.
- Sessions in terminals that the daemon owns (`metator serve`, `metator attach`, `metator pane`), the inbox (`metator inbox`), a supervisor (`metator supervise`) and the desktop app.
- `MetatorConfig` is at version 12: `notify` (6), `supervisor` (7), `options` (8), `mcp` (9), `intake` (10), `reviews` (11). Version 12 removes `paths.runs`, `paths.index`, `paths.discovery` and `paths.gates`: local state always lives under `.metator/`. An older file that sets one still loads, and the key is ignored; MetatorAI drops it the next time it writes the file.
- Workflow preconditions are checked when a run starts: `clean-tree`, `branch-ok`, `tests-green`. `index-fresh` is gone; run `metator setup` to update installed workflows. A run in your checkout now refuses on uncommitted changes when its workflow requires `clean-tree` (`--allow-dirty` starts it anyway).
- `metator doctor --gates` runs the quick gate once and reports whether it is green.
- `metator graph cycles --check` fails on an import cycle. A type-only import counts.
- `metator rules pack --files` replaces `--paths`, and `metator eval run --timeout` replaces `--timeout-ms`. The old names still work.
- `metator plan scope --dry-run` prints the scope without writing it. `plan scope` is an MCP tool again and never writes.
- In `mt-pr-review` at autonomy `L2`, the skipped approval gate grants `comment`, so the publish stage can post.
- `metator init` and `metator system discover` put warnings only in `warnings`, not in `data` as well.
